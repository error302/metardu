## Offline set-out delivery

The field screen already saved each as-staked shot locally before uploading it. Two delivery gaps remained: a successful API write was followed by an incomplete direct database insert in the general sync queue, and a lost HTTP response could cause the same immutable observation to be inserted again on retry.

The local repair removes that invalid second write, assigns each local shot a stable identifier, and sends it as `clientShotId`. API writes now use a project-scoped unique key and a conflict-safe insert. A retry returns the prior observation only when the target revision and measured/design values match; reusing an identifier for different values returns a conflict. Concurrent retries are resolved by the database uniqueness constraint. Invalid targets and stale design revisions remain on-device and are excluded from automatic retries. The field screen now lists rejected shots with their captured design revision, measurements, deltas, fix accuracy, and server reason, and can download a clearly labeled local-only JSON review file. Queue read failures report an unknown count rather than zero. The screen also displays signed E/N/RL corrections to the design point from the shared engineering evaluator. Temporary connection, authentication, and server failures remain retryable. The field screen flushes queued shots on entry, when connectivity returns, and when the app becomes visible again.

IndexedDB version 2 adds a `(projectId, syncStatus)` index and backfills status on upgrade, so a project's field screen reads only its queued and rejected records. The browser/device database upgrade and recovery behavior still needs a real mobile-browser test.

Migration `088_setout_shot_idempotency.sql` adds the nullable key and unique index. It has not been applied. ## Drainage set-out coordinate review

A follow-up review found that the drainage preview checked that the project CRS was projected but did not validate every manhole and generated station against that CRS's coordinate range. An out-of-range UTM coordinate could therefore appear ready in the preview even though the set-out API later rejected it. The shared drainage engine now validates all source and generated coordinates, suppresses the station schedule when coordinates are invalid, and carries non-blocking coordinate warnings to the output screen. API-returned warnings now pause the field-job handoff until the surveyor explicitly opens the job after review.

## Pipe set-out resource guard

The lower-level pipe station generator previously calculated and sorted every candidate station before enforcing its 20,000-station output limit, and it repeated that work for the output pass. A tiny interval could therefore exhaust time or memory before the advertised cap was reached. It now rejects intervals at or below the station de-duplication precision, bounds raw interval candidates arithmetically before allocating them, limits route inputs to 20,000 pipes / alignment vertices, and reuses the one generated station schedule. Pipe-network validation also indexes upstream/downstream membership once instead of rescanning every pipe for every manhole. Regression tests cover a subnormal interval and an oversized candidate schedule.

## OpenLayers and field-product follow-up — 2026-10-07

The core choice is sound: OpenLayers is already used as the interactive map renderer across project, field, cadastral, scheme, and orthophoto workflows. METARDU uses vector layers and editing interactions, point clustering, map search and navigation, XYZ/WMS sources, GeoTIFF display, custom projections via `proj4`, and project-aware map coordinate display. It remains a display and interaction layer; distance, area, adjustment, CRS transformation, stake-out values, and engineering results must continue to come from the existing survey engines and PostGIS, with their own numerical evidence.

The specific off-network path is the licensed XYZ downloader in `OfflineTileDownloader.tsx`, which requires provider attribution and refuses bulk pulls from public OSM and Esri tile hosts. A second, unreferenced `OfflineMapDownloader.tsx` maintained a separate `metardu-mbtiles` store, used approximate UTM-to-geographic arithmetic, and attempted direct OSM downloads. It was removed because there were no application call sites and the implementation could misplace survey data or breach tile-provider terms. Device/browser persistence and field restart behavior still require real mobile validation.

The offline tile manager previously compared cached tiles with a fixed 500 MB “quota.” It now reads the browser storage estimate through the existing offline-storage helper, labels that figure as site-origin usage, and removes the meter when the browser does not provide an estimate. Cached tile bytes remain separately visible; browser quota estimates are not a guarantee that a planned download will fit.

Do not install the proposed native stack into the Next.js application. `ol` 10.8, `proj4`, Turf, `dxf-writer`, the existing Python `pyproj`/`laspy` worker, and PostGIS already cover the current paths. `GDAL/OGR`/Fiona/GeoPandas are warranted only for a defined server-side format-conversion or raster pipeline. Shapely is appropriate if METARDU commits to its optional Python OSM-PBF extractor, but that route also requires Pyrosm, a configured regional PBF, deployment storage, startup/health semantics, indexed or bounded queries, and memory/load tests; adding packages alone would not make it production-ready. PDAL is a later choice for measured large point-cloud processing. Leaflet duplicates the current map engine. A dedicated DXF parser should be evaluated against real Civil 3D/AutoCAD fixtures before replacing or extending the guarded ASCII importer.

The map's vector-tile factory and WebGL point renderer have no production callers. Keep editable survey geometry in the existing vector/editing flow. First benchmark representative point, line, and parcel sizes on a low-memory mobile browser; then use paged/server-filtered data, generalized read-only context layers, or WebGL/vector tiles only where measurements show a bottleneck. Online OpenLayers examples now document newer versions than the installed 10.8 dependency; verify version compatibility before adopting them, and do not base field editing on unstable WebGL vector-tile APIs.
