# OpenLayers and landing-page review — 2026-10-08

## OpenLayers assessment

METARDU already has a substantial survey-map foundation. The `/map` route dynamically loads its client map; the map supports drawing and editing, vertex/segment/intersection snapping, selection, measuring, project point display, layers, geolocation, stake-out, and exports. The project-point layer requests only the current viewport, cancels superseded requests, and asks the API to aggregate dense topo points while preserving control points individually. Its OpenLayers view is EPSG:3857 for display; source coordinates are transformed for rendering. Keep all survey calculations in the engineering engine and the declared project CRS.

The map is not using every OpenLayers scaling option, and it does not need to. The vector-tile factories in `src/lib/map/vectorTileFactory.ts` and the WebGL point helper in `src/lib/map/webglPointsLayer.ts` have no production callers. They are options on the shelf, not current speed improvements. The installed OpenLayers version is 10.8.0: its `WebGLPoints` layer is deprecated in favor of `WebGLVector`, and the old helper's style updater called a `setStyle` method that the deprecated layer does not expose. I corrected the optional helper to use `WebGLVector` and its supported, typed style API; this fixes the latent defect without enabling the renderer or claiming a speedup. Keep ordinary vector layers for geometry a surveyor must select, edit, or snap to. If benchmarks show that large read-only parcels or reference data slow the map, serve those as vector tiles. If dense point rendering remains the bottleneck after server-side viewport filtering and aggregation, benchmark the existing WebGL path on the lower-end phones and tablets METARDU intends to support. Treat the rendered cluster centroid as a display summary only; it must never become a surveyed coordinate.

The next map work should verify and improve field decisions rather than add buttons: make the job's CRS, datum, units, and declaration status clear beside coordinates; retain instrument/fix metadata and observation provenance; distinguish control from topo and design from as-staked results; make offline area, sync state, and last successful upload visible; and make QA findings actionable with a link to the affected record. Browser geolocation is useful for orientation, not proof of survey-grade GNSS. Test the complete capture → save offline → restart → reconnect → review workflow with actual field devices and receivers.

Before another renderer change, record a baseline for representative small, medium, and large projects on a modest field device: time to a usable map, viewport request count/size/latency, pan/zoom responsiveness, memory, visible-point count, and behavior after loss of connectivity. Then change only the rendering path implicated by those results. OpenLayers is already the correct frontend map library here; adding Leaflet duplicates a role and will not fix missing validation or offline reliability.

## Dependency recommendations

The provided library list is a menu for specific workloads, not a bundle to install wholesale.

| Recommendation | METARDU decision |
|---|---|
| OpenLayers / Leaflet | Keep OpenLayers; do not add Leaflet. |
| `proj4` / PROJ | Keep the existing registered CRS authority and `pyproj` worker support. Do not create a second transformation path. PROJ is valuable when a transformation is explicitly defined and its accuracy/resources are known. |
| Turf | Keep for browser-friendly spatial helpers; keep authoritative survey computation in the engineering engine. |
| PostGIS / GEOS | Keep PostGIS as the spatial store/query layer. PostGIS already exposes GEOS-backed validity and geometry operations; add a separate GEOS binding only for a demonstrated worker workload. |
| GDAL/OGR, Fiona, GeoPandas | Do not put native GIS dependencies in the Next.js app. Add an isolated import/export worker only for named formats or raster workflows unsupported by the current parsers, then validate each required driver, CRS behavior, deployment image, and file-size limit. |
| `dxf-writer` / `dxf-parser` | Keep the writer and existing guarded importer. Add another parser only if real customer DXF samples expose a documented gap. Validate round-trip output in target CAD software. |
| `laspy` / PDAL | Keep current LAS/LAZ support. Add PDAL when a defined point-cloud processing workflow needs classification, filters, streaming, or COPC at scale—not just to read a file. |

This fits the current dependency footprint: JavaScript already includes `ol`, `proj4`, Turf, and `dxf-writer`; the Python worker includes `pyproj` and `laspy`/LAZ. The public OpenLayers examples can target a newer version than the installed `ol` dependency, so check the installed-version API before copying patterns. In particular, do not make a field-editing workflow depend on an experimental WebGL vector-tile API.

## Landing-page direction

The working-tree landing page is already short: one hero, a three-step workflow, pricing, and a short FAQ. That is the right scale. Do not add another feature catalogue, tool directory, technical-statistic strip, or unsupported customer claim. Keep a single clear promise, an interactive demo explicitly identified as synthetic, a small set of licensed fieldwork photos that each show a relevant workflow, one real METARDU screen after its underlying workflow is verified, and a primary action with account creation as the secondary action.

NASA Worldview is a useful reference for organizing complex map content around a clear layer list, legend, date control, compare, and share actions. Esri Field Maps is a useful reference for connecting maps to real field tasks: high-accuracy GPS, forms and attachments, task coordination, offline work, and office review. For METARDU, translate those into one clear field-to-office story, not a catalogue of every tool. Borrow their information architecture and editorial clarity, not either company's branding or web photography.
